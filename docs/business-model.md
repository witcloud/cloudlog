## 1. 项目定位与目标

**定位**：单作者（博主本人）个人博客系统。博主产出内容，读者阅读、评论、点赞。前后端分离，代码共存于同一仓库。

**目标**：

1. 博主能以 Markdown 完成「写作 → 草稿 → 发布 / 定时发布」的完整闭环，并在后台管理文章、评论、分类、标签与站点开关。
2. 读者能公开阅读已发布内容、按分类/标签/关键词检索、登录后可评论与点赞。
3. 保持可读、可自托管、可单人维护的复杂度：**任何功能选择，优先选实现面更小的那条**。

**角色总量固定为三种**：博主（`admin`）、读者（`user`）、匿名访客。不存在第四种角色，也不存在角色继承或细分权限。

## 2. 核心实体（Domain Model）

### 2.1 关系概览

```
User 1─N Post          Post N─M Tag（经 PostTag 关联）
User 1─N Comment       Category 1─N Post（可空归类）
User 1─N Like          Post 1─N Comment（parent_id 自引用，最多两级）
Post 1─1 SeoMeta       Post 1─N VisitLog
```

所有关联都是**逻辑关联，无物理外键**，完整性由应用层维护。`SiteSetting` 是独立 KV，不与任何实体关联。

### 2.2 User（用户）

| 字段 | 业务语义 | 取值与约束 |
|---|---|---|
| id | 主键 | 自增 |
| email | 登录名，唯一 | 注册需邮箱验证码；**同时是 JWT 的 subject**，改邮箱必然使现存 token 失效 |
| password | 口令 | 单向加盐散列存储，任何接口都不得返回 |
| username | 显示名，唯一 | 用户可自行修改 |
| avatar | 头像地址 | 上传后落库的是**含域名的完整 URL**，不是相对路径 |
| bio | 个人简介 | 用户可自行修改 |
| role | 角色 | `admin`（博主）/ `user`（读者），默认 `user`；注册接口恒写 `user`，提级只能由 DB 操作完成（当前后台无角色管理功能，见 §4.6） |
| status | 账号启停 | `1` 正常 / `0` 禁用；禁用**即时生效**（每次带 token 的请求都回库重载用户），无需 token 黑名单 |

用户可自行修改的字段**只有** `username` 与 `bio`（头像走上传接口）。邮箱、角色、状态不由用户自助修改。

### 2.3 Post（文章）

| 字段 | 业务语义 | 取值与约束 |
|---|---|---|
| id | 主键 | 自增 |
| title | 标题 | 必填、非空 |
| content | 正文 | 存 **Markdown 源文**，不存渲染结果；HTML 由前端渲染 |
| excerpt | 摘要 | 可空，列表页展示用 |
| cover | 封面图 | 完整 URL，可空 |
| author_id | 作者 | 服务端由登录态回填，不接受客户端指定 |
| category_id | 分类 | 可空；发布为 `published` 或转为 `scheduled` 前必须已选分类 |
| status | 生命周期状态 | `draft` / `published` / `scheduled`，默认 `draft`；语义见 §3.2 与 §4.2 |
| is_top | 置顶 | `1` 置顶，仅在默认排序中前置 |
| view_count | 阅读量 | 冗余计数，每次详情访问 +1 |
| like_count | 点赞数 | 冗余计数。**当前语义为「盲增计数」，非「去重后的点赞人数」**，见 §3 P0 缺口 |
| comment_count | 评论数 | 冗余计数，**仅 `approved` 评论计入**，扣减不得为负 |
| published_at | 首次对外可见时刻 | 可空；文章首次成为 `published` 之后不再变化；`scheduled` 期间它是可覆盖的计划时刻；`scheduled → draft` 时清空 |

### 2.4 Category / Tag / PostTag（归类）

| 实体 | 字段 | 说明 |
|---|---|---|
| Category | id、name（唯一）、description | 一篇文章**至多属于一个分类**；列表侧的 `articleCount` 是查询时派生的，不是存储字段 |
| Tag | id、name（唯一） | 文章与标签多对多；支持「合并标签」（把源标签的关联整体改写到目标标签） |
| PostTag | post_id、tag_id（联合主键） | 纯关联表，无自有业务字段 |

### 2.5 Comment（评论）

| 字段 | 业务语义 | 取值与约束 |
|---|---|---|
| id | 主键 | 自增 |
| post_id | 所属文章 | 必填 |
| user_id | 评论者 | 可空（NULL = 匿名）。但**当前 HTTP 路径无法产生匿名评论**：提交评论需登录，且服务端用会话身份覆盖请求体中的用户标识，客户端伪造他人身份的路径已封 |
| content | 正文 | 必填、非空 |
| parent_id | 回复目标 | `0` = 根评论，否则为父评论 ID；**最多两级**，不做无限嵌套 |
| status | 审核状态 | `pending` / `approved` / `rejected`；由服务端按站点开关决定，**不接受客户端指定** |

### 2.6 SiteSetting（站点开关）

KV 结构，缺省值内置于服务层，未配置即按默认生效。当前只有两个键：

| 键 | 默认 | 语义 |
|---|---|---|
| `comment_moderation` | `true` | 开启时新评论落 `pending` 需人工通过；关闭时直接 `approved` |
| `registration_enabled` | `true` | 关闭时注册接口直接拒绝，**已在注册逻辑最前处校验** |

新增开关的先例即扩展这张表的键，不新建配置表。

### 2.7 存在但当前无读写链路的实体（重要）

以下三张表**已存在于 `schema.sql`**；`seo_meta`、`visit_logs` 有对应实体类（`SeoMeta`、`VisitLog`），**`likes` 连实体类都没有**；三者在全仓都没有任何 Mapper、XML SQL 或调用方读写：

| 实体 | 真实状态 | Agent 必须避免的误解 |
|---|---|---|
| Like | 零引用，且无实体类与 Mapper。点赞走文章的 `like_count` 计数列，无去重、无取消、无法追溯谁赞过 | 不要以为「`likes` 表存在 = 点赞已去重」。要用点赞必须先建读写链路 |
| SeoMeta | 零引用。文章实体的 SEO 字段永不被填充 | 不要以为 SEO 元数据已持久化。目前只有前端自行设置文档标题 |
| VisitLog | 零引用。访问行为不入库 | 不要以为已有访问来源/IP 统计能力 |

**处理约定**：这三张表视为「已预留的表位」。启用哪一个就先为它建完整链路，不要顺手扩展另外两个。

## 4. 主要业务流程

### 4.1 注册与登录

1. 访客请求向邮箱发码 → 系统生成一次性验证码，写入 Redis（5 分钟过期），经 SMTP 投递。
2. 访客提交邮箱 + 用户名 + 口令 + 验证码 → 系统先校验注册开关（关闭则直接拒绝），再校验验证码（**校验成功即销毁，一次性**），通过后落库，角色固定为 `user`，口令单向散列。
3. 登录 → 按邮箱查用户 + 校验口令 → 返回 JWT 与用户摘要（id、用户名、头像、角色）。
4. 前端持有 token 与用户摘要（本地存储 + Pinia）；后续请求携带 token，服务端每次回库重载用户，因此禁用与角色变更下一次请求即生效。

### 4.2 写作与发布（状态机）

```
（新建 / 自动保存）→ draft
draft → published     立即发布：published_at 为空时写入当前时刻（否则保持），要求已选分类
draft → scheduled     定时发布：把计划时刻写入 published_at，要求非空且晚于当前、且已选分类；经更新接口把状态改为 scheduled 时同样要求计划时刻非空且晚于当前。带计划时刻的写入依赖 §3.2「定时发布执行」，当前后端入参不接收该字段
scheduled → published 调度器到点只改 status，published_at 沿用计划时刻（目标态，当前缺执行方）
scheduled → draft     经编辑器更新接口（`PUT /articles/{id}` 带 `status`）撤下（清空 published_at）
published → draft     经编辑器更新接口（`PUT /articles/{id}` 带 `status`）改回（现状允许，但 published_at 不回退）
```

1. 编辑器要求标题与正文非空、且已选分类才允许发布或定时；自动保存 30 秒静默写入 draft。现状：创建接口对草稿也要求 `categoryId` 非空，前端以默认分类兜底；「草稿免分类」属目标态。
2. 首次保存由后端返回新文章标识，前端据此切换到「编辑既有文章」路径，之后走更新，避免重复插入草稿行。
3. `published_at` 语义是**首次对外可见的时刻**：文章首次成为 `published` 之后不再变化；`scheduled` 期间它是可覆盖的计划时刻，`scheduled → draft` 时清空；更新时若状态转为 `published` 且该值为空才补写。
4. 插图与封面在保存前先上传到对象存储，拿到的**完整 URL** 才被写入正文或封面字段。
5. **未决语义**（不得擅自实现其中一种）：`scheduled` 的 `published_at` 存的是未来时刻；若博主在到点前手工改为 `published`，前台会显示「发布于未来」。是否改写为当前时刻，需产品裁决后再实现。

### 4.3 阅读与可见性判定

1. 列表接口只返回 `published` 内容。
2. 详情接口取到文章后先判状态：为 `published` 直接放行；否则要求请求者已登录，且**是作者本人或博主**，不满足一律按「不存在」响应（不泄露资源是否存在）。
3. 放行后累加阅读量。
4. 内容可见性的唯一真源在服务端；前端「是否显示编辑入口」只是展示层判断。

### 4.4 评论与审核

1. 登录用户提交评论，服务端以会话身份回填评论者（忽略客户端传入的用户标识），并按 `comment_moderation` 开关决定初始状态——开则 `pending`，关则 `approved`。
2. 前台只展示 `approved`；只有 `approved` 计入 `comment_count`。每条评论（含回复）各自判定，回复的展示只看自身 `status`，不继承父评论。
3. 博主在待审列表裁决：通过 → `approved` 且计数 +1；拒绝 → `rejected` 且计数不变。跨越 `approved` 边界时才增减，扣减有下限保护。裁决只有 `pending → approved` 与 `pending → rejected` 两条路径，不做回审。
4. 删除文章时其评论一并清理（后台删除路径已级联，见 §5.7 禁止事项第 7 条）。
5. 删除评论是硬删：删根评论时连带其回复一起删，`comment_count` 按被删的已通过条数扣减，下限为 `0`。

### 4.5 点赞（目标态）

1. 未登录点击 → 引导登录并可回跳原页；不产生任何写入。
2. 已登录点击 → 按当前状态选择「赞」或「取消赞」，两者都必须**幂等**（重复提交不产生第二条记录、不报错，返回当前真实状态）。
3. 计数以关联记录的实际条数**绝对重算**写回 `like_count`，不做 `+1 / -1` 盲增，以便天然幂等并顺带修正历史脏值。
4. 前端按钮状态以服务端返回值为准，不做乐观更新。

### 4.6 管理后台

博主在 `/admin/**`（要求 `admin` 角色）管理：文章全生命周期、评论审核、分类与标签（含合并）、用户启停、站点开关、概览数据。后台是**独立界面族**，不复用前台的读者视图。

### 5.2 目录与分层规范

| 规范 | 内容 |
|---|---|
| 顶层目录 | `cloudlog_api/`（后端）、`cloudlog_web/`（前端）。**README 中的 `api/`、`web/` 已过期**，按这两个名字找 |
| 后端依赖方向 | `controller → service → mapper → DB`，单向向下。禁止 controller 被 service 反向依赖、禁止 controller 直接调 mapper。现存违规：`CommentController`、`UploadController` 直接注入 `UserMapper`；新增代码不得效仿 |
| 包职责 | `controller`（入参/权限注解/组装响应）、`service`（业务规则与事务）、`mapper` + `resources/mapper/*.xml`（SQL）、`entity` / `model.dto` / `model.vo` / `model.converter`、`common`（统一响应与全局异常）、`config`、`security` |

| 新代码归属 | 与现有包位冲突时**跟随就近的既有风格**，不顺手合并历史包（现存 `dto` 与 `model/dto` 并存，属已知技术债，不在改动范围内） |
| 前后端对应 | 一个业务域一个 api 模块（前端 `src/api/*.ts`）对应一个 controller；后台接口以 `Admin` 前缀命名并置于 `/admin/**` |

### 5.3 数据获取方式（前端）

1. 后端接口前缀是 `/api/v1`（含 servlet context-path），前端 axios 实例 `baseURL` 已固定为该值；开发态由 Vite 代理转发，**前端代码不写完整域名**。
2. **组件与视图禁止直接使用 axios 或 fetch**，一律经 `src/api/*.ts` 的具名函数。全仓只允许存在一个 axios 实例。
3. 请求拦截器从本地存储读取 token 并注入 `Authorization: Bearer <token>`；无 token 时不注入该头。
4. 响应拦截器已做两件事：**解包**（调用方拿到的是统一响应体本身，需自行读 `.code` / `.data`）与**统一报错**（`code` 非 200 时自动弹提示并 reject）。因此：
   - 组件不得二次拼装同类错误提示（会双弹）；
   - 组件若需要额外处理失败，只做局部逻辑，不要再弹一条全局提示；
   - 当前拦截器**没有 401 专门处理**（不跳登录、不清 token）。需要时集中加在拦截器，不散落到各视图。
5. 视图与 store 中**不得保留演示/假数据**。现存违规有两处：①详情页评论区硬编码假评论（P0 缺口）；②详情页点赞按钮仅本地自增、不发请求（同属前端伪造可见结果）。补齐真实链路时必须把这两处本地伪造逻辑一并删除，而不是在其旁边加真实分支。

### 5.4 接口与响应约定（后端）

| 约定 | 内容 |
|---|---|
| 统一响应 | `code` + `message` + `data`。成功 `code` 恒为 `200`、`message` 为「操作成功」；失败时 `data` 为空 |
| message | **必须是可直接展示给用户的中文一句话**，前端不再二次拼装 |
| 分页 | 响应 `total` / `page` / `pageSize` / `list`；`list` 空时为 `[]` 而非空值。新接口入参统一用 `page` / `pageSize`（存量草稿接口用 `pageNum`，属历史包袱，不迁移也不扩散） |
| 错误码 | 与 HTTP 状态码同值：400 参数/业务校验、401 认证失败或账号禁用、403 越权、404 资源不存在。**禁止引入五位错误码体系** |
| 业务校验失败 | 抛运行时异常并携带中文原因，由全局兜底转 400；资源不存在抛专门的未找到异常（HTTP 与 `code` 一致） |
| 时间 | 服务端时区 `GMT+8`。出站 `LocalDateTime` 为 ISO 格式（前端统一格式化）；入站计划时刻沿用既有字符串格式 `yyyy-MM-dd HH:mm:ss` 并显式声明时区——**该格式已是对外契约的一部分**，不得单方面改。新接口不再引入旧日期类型 |
| 文档注解 | 新增/改动接口必须补齐分组、操作摘要、参数与字段描述，中文，与既有文件风格一致 |
| 排序 | 列表排序取值集合必须唯一且文档与实现一致（现状冲突见 §3.2）；改动时以**同时收口两侧**为唯一正确做法，不得只改一侧 |

### 5.5 鉴权要求

| 项 | 约束 |
|---|---|
| 会话 | 无状态，关闭 CSRF；不使用服务端 session |
| token | HMAC-SHA 系；算法由 JJWT 按密钥字节长度推导（≥32 字节 HS256，≥48 字节 HS384，≥64 字节 HS512），**本文不写死 HS256**。subject 为**邮箱**，有效期 7 天；**无刷新令牌、无黑名单、无轮换**（禁用靠每请求回库重载实现即时失效）。核对（JJWT 0.12.6 + JDK 21 实测）：47 字节 → HS256，63 字节 → HS384，64 字节 → HS512；本地配置密钥为 63 字节，故当前实际签发算法是 HS384 |
| 过滤链顺序 | 顺序即规则，自上而下：`/auth/**` 与 `/error` 放行 → `GET /articles/drafts` 要求登录 → `GET /articles/**`、`/categories/**`、`/tags/**` 放行 → 接口文档与 actuator 放行（待收紧） → `/admin/**` 要求 `ADMIN` → **其余一律要求登录** |
| 关键陷阱 | 「`GET /articles/**` 通配放行」意味着**任何新增的 `/articles/` 下 GET 子路径会自动变成公开接口**。含私有数据的 GET 端点必须显式排在通配之前（`/articles/drafts` 是唯一先例，照它做） |
| 写权限 | 文章的创建/更新/删除仅博主（方法级角色注解）。**普通登录读者只能评论、点赞、改自己的资料**，不能发文——这是真实的权限模型，不要「顺手」放开。现存例外：草稿删除接口（`DraftController`）无角色注解，任意登录用户可调用，见 §3.2 P1；不得据此放开其他写接口 |
| 属主校验 | 任何「用户操作自己资源」的接口，服务端谓词里必须显式带上属主条件（`author_id` / `user_id`）。现存反例：单条删除草稿缺作者过滤（§3.2 P1），修它的方式是补条件，不是加前端判断 |
| 身份来源 | 凡涉及「当前用户」，一律服务端从安全上下文取，**忽略请求体里的用户标识**（评论已如此，新接口照此） |
| 前端守卫 | 路由守卫（登录态、`role` 等值比较）**只是体验门槛，不是安全边界**，可被本地存储篡改绕过。真权限只在后端；禁止在前端做权限判定的兜底 |
| 敏感信息 | 真实口令/密钥只存在于本地未提交的配置文件（`application.yml`、`.env`），仓库里只放 `*.example` 模板。禁止把任何真实凭据写入代码、日志、文档或提交历史 |
| 跨域 | 当前无 CORS 配置，同源靠代理。**不要为了让某次直连成功而放开全局 CORS** |

### 5.6 存储与外部依赖

| 依赖 | 用途与边界 |
|---|---|
| MinIO | 所有上传图片（头像、正文插图、封面）。对象键为随机名 + 原扩展名，平铺不分目录。**上传返回的是拼接了域名的完整 URL 并直接落库**——换存储域名需要回刷库，这是已知代价，不要改成前端拼 |
| MinIO 校验 | 类型白名单按客户端申报的内容类型判断（jpg/png/gif/webp），单文件上限 10MB。属已知弱点，见 §6 |
| Redis | 只有两处：① 验证码（5 分钟 TTL、一次性、校验通过即销毁）；② 阅读量计数器。**未启用注解式缓存**，没有 `@Cacheable`、没有 `CacheManager`。不要为省查询随手加缓存层 |
| 阅读量口径 | Redis 与 DB **各自独立自增、互不回读**：DB 列是展示与排序的真源，Redis 侧当前无人读取（只写不读）。这是现状而非待修缺陷；改它的正当理由是削减写放大，不是修复不一致 |
| SMTP | 仅用于注册验证码。无条件装配、无开关、无降级——**邮件配置缺失会导致启动或发码失败**，涉及发码链路的改动要意识到这一点 |
| 访问日志 | 不写库（见 §2.7） |

### 5.7 禁止事项

1. 禁止引入多租户、组织架构、团队空间、协作编辑。
2. 禁止引入支付、订阅、会员、付费墙、积分、等级、签到。
3. 禁止引入 RBAC 权限矩阵、角色继承、细粒度授权表。角色只有 `admin` / `user` 两个字符串值。
4. 禁止在既有依赖之外引入新框架/新 UI 库/新状态管理/新图标体系/新缓存方案。前端一律复用既有组件库与既有样式变量。
5. 禁止引入消息队列、分布式锁、幂等表、独立的定时任务框架（Quartz、XXL-JOB 等；Spring 自带的 `@Scheduled` 属内建能力，允许）、搜索引擎、向量检索。**本项目按单实例部署假设设计**。
6. 禁止引入 MapStruct、Testcontainers、五位错误码体系、代码生成器。
7. 禁止**新增**与既有后台删除路径行为不一致的删除实现：文章删除必须连带清理标签关联与评论（后台路径已如此），不要新增一条只删主表的旁路；`likes`、`seo_meta` 链路启用时同样须随文章删除。
8. 禁止单方面修改已对外稳定的契约：响应体字段、分页入参名、计划时刻字符串格式、接口前缀。
9. 禁止以「重构」为名改动已稳定模块（阅读量双写、历史包位、JWT subject、统一响应结构）。
10. 禁止为 `Like` 引入多目标点赞抽象（`target_type` 一类）——当前只有文章可点赞。
11. 禁止在文档/注释里写「已支持」而代码未支持（§2.7 三张表与 §3 的现状列即为防此类漂移而设）。

## 6. 明确不做的范围

以下条目是**决定**，不是待办。Agent 不得自行实现，也不得「先搭个骨架」；若外部要求变更，先取得用户裁决再更新本文件。

**权限与账号**

- 不做多博主 / 作者协作 / 编辑部角色。
- 不做第三方登录（OAuth）、SSO、双因素认证。
- 不做 token 刷新、主动登出接口、token 黑名单。
- 不做站内通知、私信、关注/粉丝关系、用户主页社交化。

**内容形态**

- 只做「文章 + 分类 + 标签 + 评论」这一种内容模型。不做独立页面（Page）、图集、播客、视频、链接书签、读书笔记等并列内容类型。
- 不做评论无限嵌套（上限两级）、不做评论点赞、不做富文本评论。
- 不做正文版本历史、协同编辑、内容回滚。
- 不做多语言 / i18n。

**增长与商业化**

- 不做支付、赞赏、订阅付费、广告位、会员体系。
- 不做积分、等级、徽章、排行榜。
- 不做邮件订阅列表、推送通知、微信/微博分发集成。

**数据与运维**

- 不做 BI 看板、埋点平台、访问来源分析（`visit_logs` 保持零写入，见 §2.7）。
- 不做读写分离、分库分表、多环境配置中心、K8s。
- 不做图片裁剪/缩略图流水线/CDN 接入。
- 不做内容审核模型、敏感词库、机器反垃圾（防刷只到 §3.2 列出的频控为止）。

**已排除的技术债**（承认其存在并保留现状，不在任何改动中顺手处理）

- `Result.error` 手动返回时 HTTP 状态仍为 200。
- `dto` 与 `model/dto`、`entity` 与 `model` 包位并存。
- 阅读量 Redis 键只写不读、无过期。
- 上传类型校验信任客户端申报的内容类型、无魔数嗅探、对象无回收。
- 前端 `nprogress` 声明未使用、后台设置页依赖未声明的 `@vueuse/core`。
- 前端无测试设施；后端集成测试需外部 MySQL/Redis 才能通过。

**当前明确的下一个待决问题**（需要用户裁决，不得自动实现）

1. 定时文章被提前手工发布时，`published_at` 是否改写为当前时刻（§4.2 第 5 条）。
2. 列表排序取值以 `popular` 还是以 `hottest` 为准（§3.2、§5.4）。
3. 单条删除草稿的越权修复是否本轮纳入（§3.2、§5.5）。
